# JODU51641 / JODU51642

Two models, one flow. The ADB shell the recovery images provide is only a
foothold — it lasts a few seconds per boot until `build_type` is changed.

```text
USB-C
  -> Fastboot
  -> flash supplied recovery + recoveryfs
  -> reboot
  -> short ADB window  (~5 s, recovery boot)
  -> make ADB persistent          build_type = debug
  -> normal boot with a root adb shell
  -> install firmware             WebUI .ffw upload
  -> re-apply build_type + ACS / FOTA / heartbeat block
```

Everything below was verified on a **JODU51642** going from `40_00_00` to
`31_00_00` and back to a normal boot with persistent root ADB.

## Requirements

- Matching ODU model: **51641** or **51642**
- USB-C data cable
- ADB and Fastboot utilities on the host PC
- Matching model package:
  - `devices/51641/51641-adb.zip`
  - `devices/51642/51642-adb.zip`

Do not mix the 51641 and 51642 packages.

## 1. Enter Fastboot

Connect the ODU to the PC over USB-C.

```sh
fastboot devices
```

Press/hold the ODU reset button until Fastboot detects the device. Repeat
`fastboot devices` while doing this. Proceed only when a device serial is
displayed.

## 2. Flash the supplied recovery images

Extract the matching ZIP package and use the recovery and recoveryfs images
supplied inside it.

```sh
fastboot devices
fastboot flash recovery <provided-recovery-image>
fastboot flash recoveryfs <provided-recoveryfs-image>
fastboot reboot
```

Use the actual filenames from the matching ZIP.

## 3. Catch the ADB window

After `fastboot reboot` the ODU comes up in recovery with adbd running as
root — but only for a few seconds. Two details make or break this step:

- **adbd starts ~2.4 s before the UBI volume is attached.** A payload that
  mounts immediately fails with `MOUNT_FAIL`; wait for `/dev/ubiN_0`.
- **Run one payload at a time.** Two concurrent probes collide on the same
  mountpoint and produce spurious failures.

A payload runner is included:

```sh
./scripts/adb-once.sh scripts/probes/51642-postdowngrade.probe
SERIAL=afb84a10 ./scripts/adb-once.sh scripts/probes/51642-postdowngrade.probe
```

It polls `adb devices` every 0.2 s, fires the moment the device appears, retries
inside the window, and appends the transcript to `logs/`. Leave it running and
power-cycle the ODU; nothing needs to be typed during the window.

Confirm visibility manually if preferred:

```sh
adb devices
adb shell
```

### Manual ADB fallback

The original project notes use empty `fake_sbin` stubs to temporarily shadow
selected commands:

```sh
adb wait-for-device
adb push tools/fake_sbin /tmp/fake_sbin/

adb shell "chmod +x /tmp/fake_sbin/*; \
export PATH=/tmp/fake_sbin:$PATH; \
mount --bind /tmp/fake_sbin/pkill /usr/bin/pkill; \
mount --bind /tmp/fake_sbin/reboot /sbin/reboot; \
mount --bind /tmp/fake_sbin/recovery /usr/bin/recovery; \
which pkill; ps"

adb shell
```

## 4. Make ADB persistent

This is the step that turns a five-second window into a normal root shell.

| | |
|---|---|
| File | `/usr/etc/versions/build_type` (on the system rootfs) |
| Stock | `perf` — adbd runs **only** in recovery |
| Change | `debug` — adbd runs on the **normal** boot, as root, indefinitely |

Verified to survive reboots on both `40_00_00` and `31_00_00`. It is not a
bypass of the recovery images; the flashed recovery is only needed to make the
first edit.

Run the probe during the window:

```sh
./scripts/adb-once.sh scripts/probes/51642-postdowngrade.probe
```

Or by hand:

```sh
mkdir -p /tmp/ubi_edit
mount -t ubifs -o rw /dev/ubi1_0 /tmp/ubi_edit
cd /tmp/ubi_edit/usr/etc/versions

cp build_type build_type.bak
printf 'debug\n' > build_type
cat build_type          # debug

sync
cd /
umount /tmp/ubi_edit
```

Then power-cycle normally (not into fastboot/recovery):

```sh
adb devices             # the ODU now stays visible
adb shell 'id'          # uid=0(root)
```

> **Volume naming.** In recovery the system rootfs is `/dev/ubi1_0` (recovery's
> own fstab says `0 /system ubifs /dev/ubi1_0`). On the normal boot that same
> rootfs is simply `/` (`ubi0:rootfs`), and `/dev/ubi1_0` is a *different*
> volume — the firmware staging area mounted at `/firmware`. UBI indices follow
> attach order, so identify a volume by its contents (`usr/etc/versions`,
> `etc/hosts`), not by number. `scripts/adb-apply-51642.sh` does this by
> scanning volumes.

## 5. Install firmware

### 5.1 The `.ffw` is a container, not a zip

A JODU51642 `.ffw` starts with the ASCII magic `sErCoMm!`, followed by the
version string and a `Full` tag, and the rest of the file is **encrypted**:

- 8.00 bits/byte entropy, random tail
- no `PK\x03\x04`, no zip EOCD, no `xz` / `gzip` / `zstd` / `bzip2` /
  `squashfs` / `UBI#` / `ustar` / `ANDROID!` magic anywhere in 130 MB
- raw deflate and raw LZMA1 fail at every plausible offset and dictionary size

Nothing on the device decrypts it: `sectool` only handles TPM-sealed mTLS keys,
`SampleCOSUpdateApp` is eSIM/eUICC COS patching, and `jio_file_encryption.sh`
encrypts logs. The box decrypts the container itself during the upgrade.

**Do not attempt to unpack it by hand.**

### 5.2 Upload it through the WebUI (verified path)

The upgrade that actually worked was the one on the device's own **Software
Upgrade** page:

1. Reach the ODU's WebUI (browser, LAN, or a local proxy).
2. Open the software upgrade / firmware page.
3. Upload the matching `.ffw` and let it run to completion.

Do not interrupt power. The box decrypts the container, stages it, reboots into
recovery once, and installs it.

Expect:

- The ODU is unreachable for several minutes during the install.
- On the next normal boot, **`build_type` is back to `perf`** and the adb shell
  is gone — the install replaces the system rootfs.

> **If there is no upgrade page at all**, you are probably on `40_00_00`: that
> build ships no Sercomm web root (`/oem/www` does not exist, `/www` is a stub,
> and `/WEBSERVER/www` is Qualcomm's QCMAP UI). The JioOdu UI appears on
> `31_00_00`, which is why the WebUI route is usable after the first downgrade.

### 5.3 What the installer does internally

From recovery's `/cache/recovery/last_log`:

```text
recovery filesystem table
  0 /system ubifs /dev/ubi1_0
I:Got arguments from /cache/recovery/command
I:Set boot command "boot-recovery"
Command: "/usr/bin/recovery" "--update_package=/data/update.zip"
```

So the contract is a package at `/data/update.zip`, a command file, and a
recovery reboot. The device's own installer script spells it out
(`/usr/scm_script/cpe_sdx55_upgrade.sh`):

```sh
mkdir -p /cache/recovery
cp update_ubi.zip /data/
echo "--update_package=/data/update_ubi.zip" > /cache/recovery/command
sys_reboot recovery
```

That means a **plain** `update_ubi.zip` (plus `update_ubi.md5` for that script's
check) can be installed directly, without the WebUI and without the ACS. The
`.ffw` container cannot — it has to go through the WebUI so the box can decrypt
it first.

`cpe_sdx55_upgrade.sh` is not exposed anywhere in the UI or in a service unit on
this build, which is why the zip route is a deliberate manual operation.

### 5.4 The network route is TR-069

The only component that ingests firmware over the network is `sercomm_cwmp`:

```text
Method=8 (Download) / 9 (ScheduleDownload)
filetype "1 Firmware Upgrade Image"
handle_firmware_from_curl_stream -> /data/update.zip -> recovery
```

On `31_00_00` the binary exists but has **no systemd unit and is never started**,
so TR-069 is dormant unless an ACS URL is provisioned and the service launched.
Blocking the ACS hostnames (§8) removes that path entirely.

## 6. After the install

The new rootfs is clean: `build_type` back to `perf`, no `/etc/hosts` block, and
the version files reset to the image. Re-apply both with the same probe:

```sh
./scripts/adb-once.sh scripts/probes/51642-postdowngrade.probe
```

It waits for the UBI attach, writes `build_type=debug` (keeping a `.bak`), adds
all blocklist hostnames, then unmounts. Because ADB is dead until it runs, the
trigger has to be the recovery boot from §1–§2 again: fastboot the recovery
images, start the runner, power-cycle.

Expected transcript:

```text
RESULT:MOUNT_OK
sw_ver=JODU51642_REL_31_00_00_S
scm_ver=RC3100@2411051042
major_ver=31_00_00
build_type=perf
build_type_now=debug
HOSTS_ADDED=15
HOSTS_BLOCKED_TOTAL=16
UMOUNT_OK
END
```

Then power-cycle normally; `adb devices` stays visible and the block is live.

## 7. Version gate / downgrade preparation

Three files on the system rootfs, under `usr/etc/versions/`:

| File | Example (31_00_00) |
|---|---|
| `major_ver` | `31_00_00` |
| `scm_ver` | `RC3100@2411051042` |
| `sw_ver` | `JODU51642_REL_31_00_00_S` |

The persistent volume differs by model:

| Model | Persistent volume (from recovery) |
|---|---|
| JODU51641 | `/dev/ubi2_0` |
| JODU51642 | `/dev/ubi1_0` |

Back up and inspect first:

```sh
cp major_ver major_ver.bak
cat major_ver
```

The documented trick is to make the installed version look older than the image
you want to install. `major_ver = 0` does that:

```sh
printf '0\n' > major_ver
cat major_ver           # 0
```

Some notes for this model family use a full fake triplet instead (for example
`18`, i.e. `RC1800@…` / `…_REL_18_00_00_S`), which is only needed when the
installer compares the whole triplet. Keep the three files self-consistent — a
`major_ver` of `0` next to a `40_00_00` `sw_ver` is what made the first attempts
read as a downgrade rather than an upgrade.

When you are done:

```sh
sync
cd /
umount /tmp/ubi_edit
```

Do not reboot until the unmount succeeds.

After a successful install, leave the triplet matching the installed image
(e.g. all `31_00_00`) unless you are about to force another older image.

## 8. Disable ACS / FOTA / heartbeat through `/etc/hosts`

Mount the correct persistent volume.

```sh
# 51641
mount -t ubifs -o rw /dev/ubi2_0 /tmp/ubi_edit

# 51642
mount -t ubifs -o rw /dev/ubi1_0 /tmp/ubi_edit

cd /tmp/ubi_edit/etc
cp hosts hosts.bak
```

Append the contents of:

```text
configs/acs-blocklist.hosts
```

Then:

```sh
sync
cd /
umount /tmp/ubi_edit
```

If the ODU is already booted with persistent ADB, `/` holds the same file and can
be remounted in place instead — this is what the device's own upgrade script
does:

```sh
mount -o remount,rw /
[ -f /etc/hosts.bak ] || cp /etc/hosts /etc/hosts.bak
grep -vE '^[[:space:]]*#' /data/acs-blocklist.hosts |
while read -r ip host; do
  [ -n "$host" ] || continue
  grep -qE "[[:space:]]$host\$" /etc/hosts || echo "$ip $host" >> /etc/hosts
done
mount -o remount,ro /
```

(`/data/acs-blocklist.hosts` is `configs/acs-blocklist.hosts` pushed with
`adb push configs/acs-blocklist.hosts /data/`.)

The remount must come **before** the first write; otherwise the shell reports
`Read-only file system` while a block is being saved.

### Verify the block

`host.conf` is `order hosts,bind`, so `/etc/hosts` wins over DNS.

```sh
cat /etc/host.conf              # order hosts,bind
grep -c '^127\.0\.0\.1' /etc/hosts

for h in acs.oss.jio.com fota.jio.com jiodeviceheartbeat.jio.com; do
  ping -c1 -W1 "$h" | head -1
done
```

Each line must resolve to `127.0.0.1`:

```text
PING acs.oss.jio.com (127.0.0.1) 56(84) bytes of data.
```

**Do not use `nslookup` to check this.** It queries DNS directly and bypasses
`/etc/hosts`, so it reports the real address even when the block is working —
`ping` goes through `getaddrinfo`, which is the same path the ACS/CWMP/heartbeat
daemons use.

Read-only probe (mounts the volume, changes nothing):

```sh
./scripts/adb-once.sh scripts/probes/51642-verify.probe
```

### Revert the block

```sh
mount -o remount,rw /
cp /etc/hosts.bak /etc/hosts
mount -o remount,ro /
grep -c '^127\.0\.0\.1' /etc/hosts    # 1 (localhost only)
```

`build_type` is untouched, so ADB stays on. `scripts/probes/51642-postdowngrade.probe`
re-applies the block whenever it is wanted again — it is idempotent.

### What the blocklist actually covers

Checked against live public DNS:

| State | Hostnames |
|---|---|
| Resolves | `acs.oss.jio.com` → `49.40.8.93`, `fsreg1.acs.oss.jio.com` → `49.40.8.92`, `jiodeviceheartbeat*.jio.com` (Azure Traffic Manager), `fota.slv.kai.jphone.net`, `fota.slv.kai.jiophone.net` (Akamai), `wfr.dinj.jfdca.net`, `jpsit.jpdc.jiophone.net` |
| No record | `fota.jio.com`, `fota.jiophone.net`, `dinj.jfdca.net`, `fsreg2.acs.oss.jio.com`, `jpns.jpdc.jiophone.net`, `jpds.jpdc.jiophone.net` |

The six dead names are harmless but block nothing; they are kept because
registrations and DNS views change. Note that the `acs.oss.jio.com` VIP drops
connections from non-Jio source addresses, while `fsreg1` accepts them — so a
successful TCP probe of one proves nothing about the other.

## 9. Background behaviour worth knowing

**Heartbeat only trusts cellular.** `jio_hb_service` runs every 60 s and refuses
to report unless a `rmnet_*` interface is up:

```text
jio_jdhb_service.c:289  WAN interface is down
Stall probe: Cell:tx(0),rx(0); Eth:tx(116),rx(359)
Modem State is JIOOSCC_ABS_DIAG_MODEM_NOT_REGISTERED
```

Tethering interfaces (`bnep0`, Ethernet) do **not** satisfy it, so USB/BT
internet access does not make the box talk to Jio. Log:
`/var/volatile/log/jiologs/jio_hb_service.log`.

**There is no firmware upload UI on `40_00_00`.** See §5.2. The `/oem/www`
docroot referenced by `lighttpd.conf` lives on `persist` and simply is not
installed on that build.

**`major_ver` alone is not the gate.** The triplet is what the installer reads;
see §7.
